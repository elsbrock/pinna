# ADR 0034: The Echo Dot (5th gen): a 32-bit kernel from Amazon's MT8519 BSP

Status: proposed (2026-11-21), accepted (2026-11-21). Built
(2026-11-21): the MT8519 kernel builds and links (`kernel/build.sh mt8519` →
a 32-bit zImage and `cannoli-hvt.dtb`) with the SoC forward-ported from
Amazon's 5.4 release — the clocks, pinctrl, power domains, the SoC platform,
the device tree, SPI-NAND (the root's storage), the MT6395 PMIC, the CPLD
buttons, the microphone switch, the thermal sensors, the light sensor, the
three ring LED controllers — plus the mainline MT7663 Wi-Fi and Bluetooth,
and the U-Boot FIT boot image. The whole audio stack is ported and compiles
and links: the front end (the hard risk, patch 0210) and the cannoli machine
driver — the sound card that wires the codecs (patch 0211). It is compile-only
but faithful: the front end keeps Amazon's clock boost during the PCM copy, and
the amp fault-IRQ reporting and reset are ported into the mainline codec drivers
(`tas2764`/`max98396`), not stubbed. Two small gaps remain, both grounded in
the kernel: one latency control cannot call the private, unexported
`snd_pcm_update_hw_ptr()`, so it reads the core's maintained hw_ptr; and the
TAS5805M fault read stays a no-op because that amp is not a cannoli part.
Peripheral control uses AP-side drivers: the ring LED
controllers sit on the AP's `i2c0` in the device tree (`ringled0 =
&lp5036_i2c0_31`, `lp5036@31` on `&i2c0`), so Pinna drives the ring directly
with the mainline LED drivers (patch 0208), the same way it owns every other
peripheral. Amazon's SCP `consumer_led_controller` (the `tinysys` path) is a
firmware low-power alternative — the SCP animating the ring while the AP sleeps
— that Pinna does not use, as it does not use the audio DSP.

RAM-only bring-up on the owner's Echo Dot (5th gen), model C2N6L4, began on
2026-11-23. Linux 6.12.117 reached initialization and captured a panic at the
first PSCI SMC call: the raw EL3 upload path disables SMC. With PSCI disabled
for that diagnostic, the primary CPU reached driver initialization. A later
EL3 probe found CPU0's private interrupts assigned to Secure Group 1. Routing
only the Non-secure physical timer interrupt (INTID30) to Non-secure Group 1
let the kernel complete initcalls. A small external RAM initramfs then ran
`/init` as PID 1: it checked its PID, wrote a nonce-bound message to `/dev/kmsg`,
slept for 20 ms and wrote a second message. These diagnostic attempts returned
to stock through a watchdog; NAND remained disabled.
The Pinna root, normal secure-monitor boot path, peripheral drivers and storage
remain unvalidated. The audio codec wiring, routes and clocks
and the ring's I2C path still need measurements on the device.
The first binding audit on 2026-11-24 found a controller gap: the initial
port left `mediatek,mt8519-i2c` without an I2C core match. Patch 0214 adds
Amazon's variant, including the slave-address register at 0x94, 16-byte
FIFO transfers and the shared-channel FIFO reset. The peripheral
drivers above are present; they depend on this controller support and on
selecting the fitted codec and ring variants in the device tree.
The owner's stock device tree selects the MAX98396, TLV320ADC5140 and
IS31FL3246. A combined RAM boot with those nodes enabled reached PID 1 and
returned to verified stock on 2026-11-24. Patch 0215 removed the thermal
probe's IRQ lookup error, but sound still deferred: all four enabled I2C
controllers failed pin configuration. Amazon's device tree requests RSEL 7
for two-bit fields; its setter masks that to 3, while 6.12 rejects it.
Patch 0216 requests 3 for all five I2C pin pairs, preserving the effective
stock value. Its native regression passes; peripheral operation still needs
hardware validation. The measured IDME device type is `A4ZXE0RM7LQ7A`.
Later RAM boots verified the pin correction and captured a complete Linux
console through the wired UART (`ttyS1` on 6.12). The MAX98396, ADC5140,
MT6395, CPLD and IS31FL3246 drivers bind; the ring exposes 12 LED devices.
This establishes binding, not working audio, ring output or button events.

The next corrections address the observed port mismatches: patch 0217 matches
both codec DAI names to 6.12 and preserves the TI ADC BCLK inversion;
0218 consumes the privacy switch's stock child nodes and preserves separate
switch and button events; 0219 selects the stock IIO light driver instead of
the older input driver that requires absent metadata; and 0220 adds the
MT8519 SDIO controller data. Mainline already implements its combined tuning
and 64-step delay selection. A combined RAM boot on 2026-11-24 found the light
sensor reading, both privacy inputs registered and the MT7663 enumerated over
SDIO at SDR104. It also showed three more mismatches, now fixed: Amazon's
U-Boot writes the 5.4 codec DAI names into `/sound` on every boot, so the
machine driver maps them to the 6.12 names; the CPLD's IRQs are nested
threaded, so the privacy events request them in any context; and the MT7663
needs minstrel rate control to register.
Booting from NAND needs Amazon's GPT partition parser (patch 0221), which
creates the `ubi0` MTD partition, and a command line that attaches UBI as
stock Fire OS does and makes `ubiblock` devices for `system_a`/`system_b`.
`pinna-init` takes the slot's `ubiblock` device for dm-verity.
The stock thermal calibration reads secure fuses through OP-TEE. That path
is unavailable during raw RAM boot; the current diagnostic uses the BSP's
default calibration and does not establish calibrated temperatures.

Extends ADR 0031 (a second SoC) to a third, the MediaTek MT8519, for one
model: the Echo Dot (5th gen), `cannoli`, model C2N6L4. Amends ADR 0006 (one
kernel family on Debian's 6.12): the MT8519 is a second kernel series on the
same 6.12 base, its board support forward-ported from Amazon's own 5.4
kernel. ADR 0001's one architecture (armhf) is unchanged, and here it fits
best of all: the MT8519 runs a 32-bit kernel, so the root needs no
compatibility layer. The board layer this port needs is ADR 0032.

The board descriptions and port decisions below come from Amazon's
GPL kernel and U-Boot sources, the Linux tree, and the community port
(Gamer92000's `echo-dot-assist`, `firebreak`, `cannoli-os-builder`).
The RAM observations above establish early execution, not a working satellite.

## Context

Pinna runs on the MT8163 Echos (ADR 0001, 0006) and ADR 0031 adds the MT8516
Echos, both as a 6.12 kernel built from Debian's source with board support in
`kernel/patches`. "More Echo devices" is later work in `PRODUCT.md`. The
owner ruled out the screen devices until Pinna has screen support
(2026-11-21). Of the screenless Echos the owner has not yet ported, the Echo
Dot (5th gen) is the common recent one with a public way in.

### Unlock and boot chain

The Echo Dot (5th gen) stores everything on SPI-NAND as UBI volumes, with no
eMMC and no GPT partition table. The volumes are `boot_a`/`boot_b`,
`uboot_a`/`uboot_b`, `system_a`/`system_b`, `tee1`/`tee2`, `scp`, `mcupm`,
and four raw `brhgptlk_0..3` (the BL2/LK partitions). The boot chain, from
Amazon's `include/configs/mt8519.h` and the community port's reference:

- **Preloader** (not in the OTA), on USB as `0E8D:2000` over the test pads.
- **BL2/LK** in `brhgptlk_0..3`, which loads U-Boot.
- **U-Boot 2019.04** (AArch64) in `uboot_a`/`uboot_b`, itself a FIT. On
  NAND it runs `boot_rd_img` = `ubi read ${loadaddr} ${boot_partition}
  ${bootimage_size}`, then `bootm ${loadaddr}#${loadcfg}`. `loadaddr` is
  `0x41000000`, `loadcfg` is `conf-1`.
- **The kernel** in `boot_a`/`boot_b` is a signed FIT (`sha256,rsa2048`),
  with one configuration per board revision (`cannoli-hvt`,
  `cannoli-evt-aluminum`, `cannoli-dvt-plastic`, …) and recovery
  configurations that add a ramdisk. The FIT wraps the 32-bit `zImage` and
  the `cannoli-*.dtb` device trees.

The unlock is public but by hand, and tied to one firmware build. It needs
three wires soldered to USB test pads inside the base (the Dot has no USB
connector), and after it U-Boot boots an
image Pinna signs with its own key. How the unlock works is firebreak's; Pinna's concern is
the same as on the MT8163 and MT8516: once a bootloader that boots Pinna's
images is in place, Pinna produces the boot image it reads and never writes
the bootloader itself.

### What mainline 6.12 has, and what the MT8519 port needs

The MT8519 has **no** support in mainline, on 6.12 or on master at
2026-11-21 (v7.4-rc). There is no `clk-mt8519`, no `pinctrl-mt8519`, no
MT8519 power-domain data, no driver for its NAND controller
(`spi-mtk-snfi` covers only mt7622/mt7629/mt7986), no `mt6395` regulator,
no MT8519 audio front end, no MT8519 thermal, and no SCP binding. Unlike the
MT8516, which BayLibre's Pumpkin board brought upstream and lidar-mainline
extended, the MT8519 has only one real-world kernel: Amazon's 5.4.86. So
this port forward-ports Amazon's vendor BSP from 5.4 to 6.12 — the same kind
of work as the MT8163 (ADR 0001/0006) and MT8516 (ADR 0031) ports, with
Amazon's complete tree as the source.

The work splits three ways.

**Already in 6.12 — not ported, used as they are:**

| Part | 6.12 driver |
| --- | --- |
| Wi-Fi (MT7663, SDIO) | `mt76`/`mt7663s` (matches the MT7663 SDIO Wi-Fi function) |
| Bluetooth (MT7663) | `btmtksdio` (`chipid 0x7663`) |
| Speaker amplifier | `max98396`, `tas2764` |
| Microphone ADC | `tlv320adcx140` (the ADC5140) |
| USB | `mtu3`, `xhci-mtk`, `phy-mtk-tphy` |
| I2C, SD/SDIO cores | `i2c-mt65xx`, `mtk-sd`; the MT8519 controller matches and data need bring-up |
| PWM, watchdog, auxadc | `pwm-mediatek`, `mtk_wdt`, `mt6577_auxadc` |
| Light, temperature, current | `tsl2772` (TSL2540), `tmp108`, `ntc_thermistor`, `ina2xx` |

The MT8163's largest single piece, the 214k-line CONSYS Wi-Fi driver, has
no equal here: the MT7663's Wi-Fi and Bluetooth are mainline. Amazon's
`mt76x3` vendor driver is not carried.

**A rebase — Amazon's MT8519 data onto 6.12's MediaTek cores** (the cores
are upstream for other SoCs; the SoC-specific tables and glue move over,
adapting to API drift, as the MT8163 board support did):

| Part | Amazon source |
| --- | --- |
| Clocks | `clk-mt8519.c` and the per-block clock drivers (topckgen, infracfg_ao, apmixedsys, pericfg, m4u, imp_iic_wrap) |
| Pinctrl | `pinctrl-mt8519.c` |
| Power domains | `mtk-pm-domains` MT8519 data |
| I2C controller | `i2c-mt65xx` MT8519 register data, FIFO transfers and shared-channel reset |
| PMIC | `mt6395-regulator.c` (an I2C regulator, self-contained) |
| NAND | Amazon's `nandx` MTD stack, or MT8519 support added to `spi-mtk-snfi` |
| Small Amazon drivers | `gpio-amzncpld` (the button/switch GPIO expander), `gpio_privacy`, `led_sku_bias`, `idme` |

**The two genuine risks** — novel, entangled, or large:

- **The audio front end.** Amazon's AFE (`sound/soc/mediatek/mt8519/`, ~16k
  lines with the ADSP path) is big, and ASoC drifted since 5.4. Pinna needs
  only the direct PCM paths (ETDM2 out to the amplifier, ETDM1 in from the
  ADC, the AFE loopback reference), not the DSP, so the port is a subset —
  lidar-mainline wrote exactly such a subset for the MT8516 in ~1.6k new
  lines. It was the hardest single piece, and it is now ported (patches 0210
  and 0211, compile-only), down to the amp fault-IRQ reporting and reset; the
  status line above records what that took and the two kernel-grounded gaps
  that remain. Hardware validation remains.
- **The light ring.** The device tree places the ring's LED controller on
  the AP's own bus — `ringled0 = &lp5036_i2c0_31`, an `lp5036@31` node under
  `&i2c0` (the alternates `IS31FL3246` and `AW21036` sit beside it on the same
  bus) — so Pinna drives it directly with the mainline LED drivers (patch
  0208, enabled in `mt8519.config`), the way it owns every other peripheral.
  Amazon's firmware instead reaches the ring through the SCP co-processor over
  its `tinysys` IPC (`drivers/soc/mediatek/tinysys_ipc.c`, a
  `consumer_led_controller` fed from userland over a chardev, riding
  `mtk_scp` + `mtk_tinysys_ipi`), so the SCP can animate the ring while the AP
  sleeps. Pinna does not want that — its AP is always the controller (ADR
  0012) — so it does not port the SCP path, just as it does not port the audio
  DSP. The I2C path still needs a unit to confirm, like the rest of the board.

### The userland is already right

The MT8519 runs a 32-bit ARM (AArch32) kernel on a SoC whose bootloader,
BL31 and OP-TEE are 64-bit — Amazon's `build_kernel_config.sh` sets
`TARGET_ARCH=arm` and builds a `zImage`. Pinna's root image is armhf Debian
with static musl armv7 binaries (ADR 0001). So the Echo Dot (5th gen) runs
the same root as every other satellite, natively, with no compatibility
layer — simpler than the MT8516, whose arm64 kernel runs the armhf root as
32-bit EL0 under `CONFIG_COMPAT` (ADR 0031). The kernel package in the root
is unused at boot: the FIT in `boot_a`/`boot_b` carries the kernel.

## Decision

1. **The MT8519 is Pinna's third SoC**, for one model, the Echo Dot (5th
   gen). One kernel series, one boot image layout, one board description
   (ADR 0032).
2. **A 32-bit ARM kernel on Debian's 6.12** (ADR 0006), its board support
   forward-ported from Amazon's 5.4.86 BSP as a patch series. The root is
   the armhf image every satellite runs, with no compatibility layer.
   - `kernel/build.sh` gains an `mt8519` variant: `arch=arm`, the armhf
     cross compiler, targets `zImage` and the `cannoli-*.dtb` device trees.
     `mt8519.config` is its fragment. The MT8519 patches are numbered from
     0201; the MT8163 and MT8516 variants do not apply them, and the MT8519
     variant does not apply the others.
   - The port lands incrementally, lowest layer first: clocks, pinctrl,
     power domains and the NAND controller (a kernel that reaches a serial
     console and its storage), then the PMIC, the small Amazon drivers and
     the audio front end, then the ring. Each layer is one patch or a small
     series, credited to Amazon's release, with a config fragment change.
   - Moving the MT8519 to a newer kernel than the MT8163 and MT8516 is the
     fallback only if 6.12 costs more than it saves; that would need its own
     ADR. Mainline gains nothing here — the MT8519 is absent from v7.4 too.
3. **The boot image is a U-Boot FIT** (`.itb`), not the Android boot image
   of the MT8163 and MT8516. `pinna-bootimg` gains a FIT builder: a 32-bit
   `zImage`, the `cannoli-*.dtb` device trees, one configuration per board
   revision, and recovery configurations that add a ramdisk. U-Boot reads it
   from `boot_a`/`boot_b` with `ubi read` and `bootm …#conf-1`. The exact
   load and entry addresses and the configuration names are read from the
   stock boot FIT on a unit before the first image is written.
4. **Storage is NAND and UBI**, not eMMC and GPT. `pinna-init`,
   `pinna-bootctl` and the updater find the boot and system volumes by UBI
   volume name, not by GPT name. This is the one place the MT8163 and MT8516
   storage model does not carry over; it is built once a unit is at hand and
   the volume layout and the bootloader's slot record are read.
5. **Firmware is fetched, not committed** (ADR 0001). The MT7663's Wi-Fi and
   Bluetooth firmware comes from `static.iodev.org/pinna/firmware/cannoli/…`,
   per board and release, with `mt7663` firmware from linux-firmware where it
   is redistributable. Amazon's speaker tuning is not committed.
6. **Not now, and kept as research:** the Echo Dot with clock (5th gen)
   (`cheesecake`, C4E8S3) and the Echo Pop (`churro`, also MT8519) — no
   public unlock. They share this kernel if one appears.
7. **Nothing is written to a device before the owner has one and agrees.**
   The first device steps, in order:
   - check the label says C2N6L4, and the firmware is build 8349 (`NS6575`);
   - note that the unlock needs soldered wires and is tied to that build;
   - back up the whole NAND (every UBI volume and the raw `brhgptlk_0..3`)
     before anything is written;
   - read the UBI volume layout and sizes, the board revision and which
     amplifier, ADC and LED controller the unit carries, the stock boot
     FIT's configurations and load addresses, the idme record, and the
     bootloader's slot record;
   - decide whether the ring can be driven over I2C or needs the SCP.

## How the design keeps the goals

- **Be safe to install and update:** the Echo Dot (5th gen) keeps A/B slots
  (`boot_a`/`boot_b`, `system_a`/`system_b`) and a bootloader Pinna never
  writes, as on the MT8163 and MT8516. firebreak works over the
  test pads with no working system, so a satellite with both slots broken
  can still be recovered — the owner keeps the wires and a backup. Until it
  is shown on a unit that the bootloader boots Pinna's FIT by its slot record
  and that the updater can write a UBI volume safely, the port is not offered
  to owners.
- **Use standard parts:** the Wi-Fi, the Bluetooth, the codecs and the SoC
  peripherals are mainline drivers. The clocks, pinctrl, power domains and
  PMIC are rebased onto mainline's MediaTek cores and are candidates for
  upstream, as the MT8163 and MT8516 board support is. The audio front end is
  written the same way.
- **Stay open:** Amazon's Wi-Fi firmware and speaker tuning are not
  committed; they are fetched from `static.iodev.org`, as the MT8163's and
  MT8516's are.
- **Make development pleasant:** one root image and one Rust toolchain for
  every satellite, 32-bit native on this SoC. The kernel build adds the
  `mt8519` variant; the virtual Echo Dot and its tests keep covering the
  userland all boards share.

## Consequences

- `pinna-bootimg` gains a `fit` module: a FIT builder (`fit-pack`) and a
  reader that prints a FIT's images and configurations (`fit-info`). Signing
  follows the bootloader's trust model, read on a unit.
- `pinna-init`, `pinna-bootctl` and the updater gain a UBI volume lookup
  beside the GPT one, chosen by the board's storage kind. The MT8519's slot
  record is read before they write it.
- `pinna-board` gains an `EchoDot5` model and board (ADR 0032): the CPLD
  key codes, the `gpio-privacy` switch, the ring, the sound card with its
  ETDM PCMs and 3 microphones, and the amplifier the unit carries. Which
  amplifier, ADC and LED controller a board revision has is read from the
  device.
- `pinna-audio` gains a 3-microphone front end with the reference on the AFE
  loopback. The beamformer, the echo canceller and the wake word thresholds
  were tuned on the MT8163 array; they need measurements on this array before
  owners use it.
- The kernel grows from two board families to three. Each needs a device to
  test, and no CI runs device tests (AGENTS.md).
- The browser installer (ADR 0016) does not cover the Echo Dot (5th gen):
  its install needs soldered wires and a firmware-build check, so it stays a
  by-hand port until that changes.
- A unit is now available for RAM-only bring-up. Storage integration, the
  board description, audio and ring validation, and persistent installation
  remain pending their device evidence and the owner's approval.
