# ADR 0035: The Echo Dot (5th gen): a 32-bit kernel from Amazon's MT8519 BSP

Status: proposed (2026-11-21), accepted (2026-11-21). Built
(2026-11-21): the MT8519 kernel builds and links (`kernel/build.sh mt8519` →
a 32-bit zImage, `cannoli-hvt.dtb` and `cannoli-dvt-plastic.dtb`) with the SoC forward-ported from
Amazon's 5.4 release — the clocks, pinctrl, power domains, the SoC platform,
the device tree, SPI-NAND (the root's storage), the MT6395 PMIC, the CPLD
buttons, the microphone switch, the thermal sensors, the light sensor, the
three ring LED controllers — plus the mainline MT7663 Wi-Fi and Bluetooth,
and the U-Boot FIT boot image. The whole audio stack is ported and compiles
and links: the front end (the hard risk, patch 0210) and the cannoli machine
driver — the sound card that wires the codecs (patch 0211). It is compile-only
but faithful: the front end keeps Amazon's clock boost during the PCM copy, and
the amp fault-IRQ reporting and reset are ported into the mainline codec drivers
(`tas2764`/`max98396`), not stubbed. Two small gaps remain, both grounded in
the kernel: one latency control cannot call the private, unexported
`snd_pcm_update_hw_ptr()`, so it reads the core's maintained hw_ptr; and the
TAS5805M fault read stays a no-op because that amp is not a cannoli part.
Peripheral control uses AP-side drivers: the ring LED
controllers sit on the AP's `i2c0` in the device tree, so Pinna drives the ring
directly, the same way it owns every other peripheral. On a normal boot U-Boot
enables the LED controller, amplifier and ADC the unit carries; a `-recovery`
configuration skips that (TECHO5 discussion #610, on Amazon's kernel). On the
owner's unit (PVT, plastic) those are the IS31FL3246, the MAX98396 and the
ADC5140: the stock device tree enables them, and Pinna's RAM boot bound them,
with the ring as 12 LED class devices `is31fl3246:ledmod_0..11` (2026-11-24).
Pinna drives that ring through patch 0208's IS31FL3246 driver and Amazon's RGB
LED class. Amazon's SCP `consumer_led_controller` (the `tinysys` path) is a
firmware low-power alternative — the SCP animating the ring while the AP sleeps
— that Pinna does not use, as it does not use the audio DSP.

RAM-only bring-up on the owner's Echo Dot (5th gen), model C2N6L4, began on
2026-11-23. Linux 6.12.117 reached initialization and captured a panic at the
first PSCI SMC call: the raw EL3 upload path disables SMC. With PSCI disabled
for that diagnostic, the primary CPU reached driver initialization. A later
EL3 probe found CPU0's private interrupts assigned to Secure Group 1. Routing
only the Non-secure physical timer interrupt (INTID30) to Non-secure Group 1
let the kernel complete initcalls. A small external RAM initramfs then ran
`/init` as PID 1: it checked its PID, wrote a nonce-bound message to `/dev/kmsg`,
slept for 20 ms and wrote a second message. These diagnostic attempts returned
to stock through a watchdog; NAND remained disabled.
These RAM-only attempts validated early execution only. Pinna's root has since
booted from NAND on the same unit (see the 2026-11-26 status below).
The first binding audit on 2026-11-24 found a controller gap: the initial
port left `mediatek,mt8519-i2c` without an I2C core match. Patch 0214 adds
Amazon's variant, including the slave-address register at 0x94, 16-byte
FIFO transfers and the shared-channel FIFO reset. The peripheral
drivers above are present; they depend on this controller support and on
selecting the fitted codec and ring variants in the device tree.
The owner's stock device tree selects the MAX98396, TLV320ADC5140 and
IS31FL3246. A combined RAM boot with those nodes enabled reached PID 1 and
returned to verified stock on 2026-11-24. Patch 0215 removed the thermal
probe's IRQ lookup error, but sound still deferred: all four enabled I2C
controllers failed pin configuration. Amazon's device tree requests RSEL 7
for two-bit fields; its setter masks that to 3, while 6.12 rejects it.
Patch 0216 requests 3 for all five I2C pin pairs, preserving the effective
stock value. Its native regression passes; peripheral operation still needs
hardware validation. The measured IDME device type is `A4ZXE0RM7LQ7A`.
Later RAM boots verified the pin correction and captured a complete Linux
console through the wired UART (`ttyS1` on 6.12). The MAX98396, ADC5140,
MT6395, CPLD and IS31FL3246 drivers bind; the ring exposes 12 LED devices.
This establishes binding, not working audio, ring output or button events.

The next corrections address the observed port mismatches: patch 0217 matches
both codec DAI names to 6.12 and preserves the TI ADC BCLK inversion;
0218 consumes the privacy switch's stock child nodes and preserves separate
switch and button events; 0219 selects the stock IIO light driver instead of
the older input driver that requires absent metadata; and 0220 adds the
MT8519 SDIO controller data. Mainline already implements its combined tuning
and 64-step delay selection. A combined RAM boot on 2026-11-24 found the light
sensor reading, both privacy inputs registered and the MT7663 enumerated over
SDIO at SDR104 (patch 0227 later dropped SDIO to 50 MHz: the MT7663 timed
out at SDR104, commit 6928c59). It also showed three more mismatches, now fixed: Amazon's
U-Boot writes the 5.4 codec DAI names into `/sound` on every boot, so the
machine driver maps them to the 6.12 names; the CPLD's IRQs are nested
threaded, so the privacy events request them in any context; and the MT7663
needs minstrel rate control to register.
Booting from NAND needs Amazon's GPT partition parser (patch 0221): a GPT at
the start of NAND names the MTD partitions, `ubi0` among them, and a command line that attaches UBI as
stock Fire OS does and makes `ubiblock` devices for `system_a`/`system_b`.
`pinna-init` takes the slot's `ubiblock` device for dm-verity.
The stock thermal calibration reads secure fuses through OP-TEE. That path
is unavailable during raw RAM boot; the current diagnostic uses the BSP's
default calibration and does not establish calibrated temperatures.

Userland built (2026-11-24), with the tests that run without hardware. It has
since run on the unit (see below). The
Echo Dot (5th gen) has a board description (`EchoDot5`, idme
`A4ZXE0RM7LQ7A`, read on the owner's unit), a ring driver for the LED class
devices and the boot-stage ring on them, the MT8519 mixer sequences, a speaker
path that plays at the PCM's 96 kHz, a capture front end for its 32-bit
96 kHz PCM, a beamformer designed for its three microphones, and its own
PipeWire microphone graph (Decision 8). Patch 0222 gives the kernel the
watchdog's match.

On a C2N6L4 on 2026-11-26 Pinna's root booted from `system_a`, installed from
TWRP with `scripts/install-echo-dot-5.sh` (Decision 10). The ring, the buttons,
the microphone switch, the speaker, the wake word and Home Assistant worked,
and the A/B test ran on the unit (commit 306da31; the code comments dated
C2N6L4 2026-11-26 in `mkosi/mkosi.extra/usr/libexec/pinna/pipewire`,
`pinna-regdb.service` and `crates/pinna-update/src/writer.rs`; the "What works"
list in `website/src/content/docs/devices.md`): an update wrote slot b and it
was marked good, a broken update in slot a was retired by U-Boot after its
tries and slot b started, and an update back into slot a was marked good
(Decision 9). UL9 delivers its six lanes (C2N6L4, 2026-11-26, with
PipeWire stopped): the three microphones on lanes 0 to 2 (-54 to -52 dBFS
in a quiet room), lane 3 digitally silent, and DL2 looped back on lanes 4
and 5, where a -50 dBFS tone played on DL2 read back at -50.0 dBFS peak for
exactly its second. An earlier reading of only lanes 0 and 1 predates the
converter fixes (patches 0232 and 0233) and the switches the PipeWire
wrapper sets. Not measured: the echo canceller's result over music.

Fourteen patches followed the first boots, each from a measurement on that
unit on 2026-11-26 (`git log --oneline -- kernel/patches/0223*` and so on):

- 0223 nandx: the sub-page write option, so UBI attaches read-write.
- 0224 `gpio-amzncpld`: child interrupts go to their handlers, not a nested
  primary handler that fired every 20 ms.
- 0225 clocks: the I2C wrapper's bus clock is on while its gates are read;
  without it the boot hung 1.48 s in.
- 0226 `mtu3`: VBUS is forced valid where no pin senses it, so USB enumerates.
- 0227 device tree: SDIO runs at 50 MHz, because the MT7663 timed out at
  SDR104 (commit 6928c59).
- 0228 `mt76`: the 0x7653 efuse of this unit's MT7663 is accepted; without it
  the radio received nothing.
- 0229 `btmtksdio`: the MT7663's Bluetooth waits for its Wi-Fi to start.
- 0230 pinctrl: default bias on PUPD R1/R0 pins, so the NAND probe succeeds.
- 0231 ASoC: a device tree codec gets its own link component.
- 0232 device tree: the ADC stays out of shutdown.
- 0233 ASoC: the ADC runs as clock provider on eTDM1.
- 0234 ASoC: the AFE gets its buffers at the audio bus's DRAM address.
- 0235 clocks: the audio MCLK dividers round to the closest rate.
- 0236 ASoC: the eTDM ports use their own parameters, not the front end's.

Extends ADR 0031 (a second SoC) to a third, the MediaTek MT8519, for one
model: the Echo Dot (5th gen), `cannoli`, model C2N6L4. Amends ADR 0006 (one
kernel family on Debian's 6.12): the MT8519 is a second kernel series on the
same 6.12 base, its board support forward-ported from Amazon's own 5.4
kernel. ADR 0001's one architecture (armhf) is unchanged, and here it fits
best of all: the MT8519 runs a 32-bit kernel, so the root needs no
compatibility layer. The board layer this port needs is ADR 0032.

The board descriptions and port decisions below come from Amazon's
GPL kernel and U-Boot sources, the Linux tree, and the community port
(Gamer92000's `echo-dot-assist`, `firebreak`, `cannoli-os-builder`).
The RAM observations above establish early execution, not a working satellite.

## Context

Pinna runs on the MT8163 Echos (ADR 0001, 0006) and ADR 0031 adds the MT8516
Echos, both as a 6.12 kernel built from Debian's source with board support in
`kernel/patches`. "More Echo devices" is later work in `PRODUCT.md`. The
owner ruled out the screen devices until Pinna has screen support
(2026-11-21). Of the screenless Echos the owner has not yet ported, the Echo
Dot (5th gen) is the common recent one with a public way in.

### Unlock and boot chain

The Echo Dot (5th gen) stores everything on SPI-NAND as UBI volumes, with no
eMMC. A GPT at the start of NAND names the MTD partitions, `ubi0` among them
(patch 0221). The volumes are `boot_a`/`boot_b`,
`uboot_a`/`uboot_b`, `system_a`/`system_b`, `tee1`/`tee2`, `scp`, `mcupm`,
`misc` (the bootloader command and the slot record, in use since commit
4006676), `userdata` (UBIFS, mounted as `/var`), and four raw `brhgptlk_0..3` (the BL2/LK partitions). The boot chain, from
Amazon's `include/configs/mt8519.h` and the community port's reference:

- **Preloader** (not in the OTA), on USB as `0E8D:2000` over the test pads.
- **BL2/LK** in `brhgptlk_0..3`, which loads U-Boot.
- **U-Boot 2019.04** (AArch64) in `uboot_a`/`uboot_b`, itself a FIT. On
  NAND it runs `boot_rd_img` = `ubi read ${loadaddr} ${boot_partition}
  ${bootimage_size}`, then `bootm ${loadaddr}#${loadcfg}`. `loadaddr` is
  `0x41000000`, `loadcfg` is `conf-1`.
- **The kernel** in `boot_a`/`boot_b` is a FIT. Stock Fire OS's is signed
  (`sha256,rsa2048`), with one configuration per board revision
  (`cannoli-hvt`, `cannoli-evt-aluminum`, `cannoli-dvt-plastic`,
  `cannoli-pvt-plastic`, …) and recovery configurations that add a ramdisk.
  The FIT wraps the 32-bit `zImage` and the `cannoli-*.dtb` device trees.
  Pinna's FIT (the `fit` recipe in the `justfile`) packs one device tree,
  `cannoli-dvt-plastic.dtb` (patch 0212), under two configuration names,
  `cannoli-pvt-plastic` (the default, and the name a C2N6L4's U-Boot asks for;
  commit f012ecf) and `conf-1`, both with the initramfs. So the PVT
  configuration name boots the DVT-plastic tree.

The unlock is public but by hand, and tied to one firmware build. It needs
three wires soldered to USB test pads under its foot (the Dot has no USB
connector, so the pads are its USB, as the Echo (2nd gen)'s base pins are), and after it U-Boot boots an
image Pinna builds. That image carries only a `sha256` hash per image, no
signature node (`pinna-bootimg`'s FIT, `src/lib.rs`): the root's integrity
comes from the root's footer, which `pinna-init` checks against the
compiled-in release key, and dm-verity over the slot. How the unlock works is firebreak's; Pinna's concern is
the same as on the MT8163 and MT8516: once a bootloader that boots Pinna's
images is in place, Pinna produces the boot image it reads and never writes
the bootloader itself.

### What mainline 6.12 has, and what the MT8519 port needs

The MT8519 has **no** support in mainline, on 6.12 or on master at
2026-11-21 (v7.4-rc). There is no `clk-mt8519`, no `pinctrl-mt8519`, no
MT8519 power-domain data, no driver for its NAND controller
(`spi-mtk-snfi` covers only mt7622/mt7629/mt7986), no `mt6395` regulator,
no MT8519 audio front end, no MT8519 thermal, and no SCP binding. Unlike the
MT8516, which BayLibre's Pumpkin board brought upstream and lidar-mainline
extended, the MT8519 has only one real-world kernel: Amazon's 5.4.86. So
this port forward-ports Amazon's vendor BSP from 5.4 to 6.12 — the same kind
of work as the MT8163 (ADR 0001/0006) and MT8516 (ADR 0031) ports, with
Amazon's complete tree as the source.

The work splits three ways.

**Already in 6.12 — not ported. Four of these needed a patch to work on this
board (patches 0226, 0228, 0229 and 0233, listed above):**

| Part | 6.12 driver |
| --- | --- |
| Wi-Fi (MT7663, SDIO) | `mt76`/`mt7663s` (matches the MT7663 SDIO Wi-Fi function; patch 0228) |
| Bluetooth (MT7663) | `btmtksdio` (`chipid 0x7663`; patch 0229) |
| Speaker amplifier | `max98396`, `tas2764` |
| Microphone ADC | `tlv320adcx140` (the ADC5140; patch 0233) |
| USB | `mtu3` (patch 0226), `xhci-mtk`, `phy-mtk-tphy` |
| I2C, SD/SDIO cores | `i2c-mt65xx`, `mtk-sd`; the MT8519 controller matches and data need bring-up |
| PWM, auxadc | `pwm-mediatek`, `mt6577_auxadc` |
| Light, temperature, current | `tsl2772` (TSL2540), `tmp108`, `ntc_thermistor`, `ina2xx` |

The watchdog is mainline's `mtk_wdt` too, but 6.12 has no match for the
device tree's `mediatek,mt8519-rgu`: patch 0222 adds it with Amazon's data
(the mt6589 register layout, 18 TOPRGU software resets).

The MT8163's largest single piece, the 214k-line CONSYS Wi-Fi driver, has
no equal here: the MT7663's Wi-Fi and Bluetooth are mainline. Amazon's
`mt76x3` vendor driver is not carried.

**A rebase — Amazon's MT8519 data onto 6.12's MediaTek cores** (the cores
are upstream for other SoCs; the SoC-specific tables and glue move over,
adapting to API drift, as the MT8163 board support did):

| Part | Amazon source |
| --- | --- |
| Clocks | `clk-mt8519.c` and the per-block clock drivers (topckgen, infracfg_ao, apmixedsys, pericfg, m4u, imp_iic_wrap) |
| Pinctrl | `pinctrl-mt8519.c` |
| Power domains | `mtk-pm-domains` MT8519 data |
| I2C controller | `i2c-mt65xx` MT8519 register data, FIFO transfers and shared-channel reset |
| PMIC | `mt6395-regulator.c` (an I2C regulator, self-contained) |
| NAND | Amazon's `nandx` MTD stack, or MT8519 support added to `spi-mtk-snfi` |
| Small Amazon drivers | `gpio-amzncpld` (the button/switch GPIO expander), `gpio_privacy`, `led_sku_bias`, `idme` |

**The two genuine risks** — novel, entangled, or large:

- **The audio front end.** Amazon's AFE (`sound/soc/mediatek/mt8519/`, ~16k
  lines with the ADSP path) is big, and ASoC drifted since 5.4. Pinna needs
  only the direct PCM paths (ETDM2 out to the amplifier, ETDM1 in from the
  ADC, the AFE loopback reference), not the DSP, so the port is a subset —
  lidar-mainline wrote exactly such a subset for the MT8516 in ~1.6k new
  lines. It was the hardest single piece, and it is now ported (patches 0210
  and 0211, compile-only), down to the amp fault-IRQ reporting and reset; the
  status line above records what that took and the two kernel-grounded gaps
  that remain. Hardware validation remains.
- **The light ring.** The device tree places the ring's LED controller on
  the AP's own bus — `ringled0 = &lp5036_i2c0_31`, an `lp5036@31` node under
  `&i2c0`, with the alternates `IS31FL3246` and `AW21036` beside it, all
  disabled until U-Boot enables the fitted one — so Pinna drives it directly
  (the LP5036 with mainline's driver, the other two with patch 0208, all
  enabled in `mt8519.config`), the way it owns every other peripheral.
  Amazon's firmware instead reaches the ring through the SCP co-processor over
  its `tinysys` IPC (`drivers/soc/mediatek/tinysys_ipc.c`, a
  `consumer_led_controller` fed from userland over a chardev, riding
  `mtk_scp` + `mtk_tinysys_ipi`), so the SCP can animate the ring while the AP
  sleeps. Pinna does not want that — its AP is always the controller (ADR
  0012) — so it does not port the SCP path, just as it does not port the audio
  DSP. On the owner's unit the IS31FL3246 binds and exposes its 12 LEDs
  (RAM boot, 2026-11-24), and the ring lights from Pinna's root (C2N6L4,
  2026-11-26).

### The userland is already right

The MT8519 runs a 32-bit ARM (AArch32) kernel on a SoC whose bootloader,
BL31 and OP-TEE are 64-bit — Amazon's `build_kernel_config.sh` sets
`TARGET_ARCH=arm` and builds a `zImage`. Pinna's root image is armhf Debian
with static musl armv7 binaries (ADR 0001). So the Echo Dot (5th gen) runs
the same root as every other satellite, natively, with no compatibility
layer — simpler than the MT8516, whose arm64 kernel runs the armhf root as
32-bit EL0 under `CONFIG_COMPAT` (ADR 0031). The kernel package in the root
is unused at boot: the FIT in `boot_a`/`boot_b` carries the kernel.

## Decision

1. **The MT8519 is Pinna's third SoC**, for one model, the Echo Dot (5th
   gen). One kernel series, one boot image layout, one board description
   (ADR 0032).
2. **A 32-bit ARM kernel on Debian's 6.12** (ADR 0006), its board support
   forward-ported from Amazon's 5.4.86 BSP as a patch series. The root is
   the armhf image every satellite runs, with no compatibility layer.
   - `kernel/build.sh` gains an `mt8519` variant: `arch=arm`, the armhf
     cross compiler, targets `zImage` and the `cannoli-*.dtb` device trees.
     `mt8519.config` is its fragment. The MT8519 patches are numbered from
     0201. Every variant applies every patch (`kernel/build.sh`,
     `kernel/source.env`) and builds the parts its config selects, so a patch
     that touches a shared driver must gate itself by chip or `compatible`.
     Patch 0229, for example, makes `btmtksdio` wait only for chipid 0x7663,
     so the MT7668 Echos don't wait (commit 97b1407).
   - The port lands incrementally, lowest layer first: clocks, pinctrl,
     power domains and the NAND controller (a kernel that reaches a serial
     console and its storage), then the PMIC, the small Amazon drivers and
     the audio front end, then the ring. Each layer is one patch or a small
     series, credited to Amazon's release, with a config fragment change.
   - Moving the MT8519 to a newer kernel than the MT8163 and MT8516 is the
     fallback only if 6.12 costs more than it saves; that would need its own
     ADR. Mainline gains nothing here — the MT8519 is absent from v7.4 too.
3. **The boot image is a U-Boot FIT** (`.itb`), not the Android boot image
   of the MT8163 and MT8516. `pinna-bootimg` gains a FIT builder: a 32-bit
   `zImage`, the `cannoli-*.dtb` device trees, one configuration per board
   revision, and recovery configurations that add a ramdisk. U-Boot reads it
   from `boot_a`/`boot_b` with `ubi read` and `bootm …#conf-1`. Pinna's FIT
   carries one device tree, `cannoli-dvt-plastic.dtb` (patch 0212), under the
   configurations `cannoli-pvt-plastic` (the default; the name a C2N6L4's
   U-Boot asks for, commit f012ecf) and `conf-1`, both with the initramfs. The
   load and entry addresses and the configuration names were read from the
   stock boot FIT on a unit.
4. **Storage is NAND and UBI**, not eMMC and GPT. `pinna-init`,
   `pinna-bootctl` and the updater find the boot and system volumes by UBI
   volume name, not by GPT name. This is the one place the MT8163 and MT8516
   storage model does not carry over; it is built once a unit is at hand and
   the volume layout and the bootloader's slot record are read.
   When Pinna replaces Fire OS on the Echo Dot (5th gen), it uses the whole
   UBIFS `userdata` volume for persistent `/var`. The stock boot log confirms
   that `userdata` is UBIFS. The image mounts the volume by name and expects
   an existing filesystem. On GPT boards, `PARTLABEL=userdata` still uses
   ext4 (ADR 0001).
5. **Firmware is fetched, not committed** (ADR 0001). The MT7663's Wi-Fi and
   Bluetooth firmware (`mt7663pr2h.bin`, `mt7663_n9_v3.bin`) comes from
   linux-firmware on kernel.org (`scripts/fetch-firmware.sh`) and is built
   into the kernel with `CONFIG_EXTRA_FIRMWARE` (`kernel/mt8519.config`),
   because the drivers load it at probe, before the root is mounted. Amazon's
   speaker tuning is not committed.
6. **Not now, and kept as research:** the Echo Dot with clock (5th gen)
   (`cheesecake`, C4E8S3) and the Echo Pop (`churro`, also MT8519) — no
   public unlock. They share this kernel if one appears.
7. **Nothing is written to a device before the owner has one and agrees.**
   The first device steps, in order:
   - check the label says C2N6L4, and the firmware is build 8349 (`NS6575`);
   - note that the unlock needs soldered wires and is tied to that build;
   - back up the whole NAND (every UBI volume and the raw `brhgptlk_0..3`)
     before anything is written;
   - read the UBI volume layout and sizes, the board revision and which
     amplifier, ADC and LED controller the unit carries, the stock boot
     FIT's configurations and load addresses, the idme record, and the
     bootloader's slot record;
   - decide whether the ring can be driven over I2C or needs the SCP:
     decided, over I2C (the IS31FL3246 binds on the AP, 2026-11-24).
8. **Userland on the MT8519** (2026-11-24). Amends ADR 0004 and ADR 0033 for
   this board; the MT8163's graph and speaker path are unchanged.
   - **One combination of parts.** The board description covers what the
     owner's unit carries: the MAX98396, the ADC5140 and the IS31FL3246.
     The kernel takes the fitted parts from U-Boot's device tree, but a unit
     with the TAS2764, the AK5704, the LP5036 or the AW21036 gets no speaker,
     microphones or ring from Pinna until it is described and measured.
   - **The speaker plays at the PCM's rate.** DL2 runs at a fixed 96 kHz
     (eTDM2). Pinna keeps mixing, timing and its speaker chain at 48 kHz and
     upsamples by 2 just before the player; the hardware pointer is converted
     back to 48 kHz frames for the timed source (ADR 0027). The MAX98396
     powers with the stream through DAPM, so the MT8519 has no amp
     sequence at open or close.
   - **The mixer.** The AFE routes come from TECHO5's measurements on a
     C2N6L4 under Amazon's kernel, whose AFE driver Pinna ports (patch
     0210): DL2 to O04/O05, the ADC's slots to UL9's channels 0–3, DL2 looped
     back to channels 4–5. The codec controls are mainline's names; the ADC's
     are written, and the converter's switches are required (below); the mixer
     still skips a control that a board lacks.
   - **A graph of its own, chosen at run time.** One read-only root serves
     every SoC, so `pinna-pipewire.service` runs a wrapper that starts
     `pipewire -c pinna-echo-dot-5.conf` on an MT8519. The graph keeps the
     MT8163's node names, so pinnad needs no change: `dot_mics` opens UL9 at
     96 kHz and PipeWire resamples it to the 16 kHz graph; `dot_wake` runs
     `pinna_wake` over its six lanes, and the plugin reads the board for the
     microphones, the loopback lane the speaker plays and the array the
     ring's beams are designed for (ADR 0004).
   - **The wake word hears the three microphones averaged**, cancelled
     linearly from loopback lane 4, as on every board (ADR 0004, ADR 0033).
     TECHO5 measured on a C2N6L4 that microphone 2 alone hears the speaker
     6 dB less than the other two, and that for the wake word over music it
     beat the three-microphone average; Pinna hasn't measured that.
   - **UL9 delivers its six lanes** on Pinna's kernel (C2N6L4,
     2026-11-26, the release with patches 0232 to 0236 and the PipeWire
     wrapper's switches): the three microphones, lane 3 digitally silent, and
     the loopback on lanes 4 and 5, so the canceller has its reference. An
     earlier reading of two lanes predates those fixes. The AFE driver and
     the device trees are
     Amazon's, ported with changes where 6.12 or the unit differed: patches
     0234 and 0236 change `mt8519-afe-pcm.c` (the audio bus's DRAM window and
     the eTDM ports' own parameters); 0217, 0232, 0233 and 0234 change the
     device trees (DAI names and the ADC's BCLK, the ADC out of shutdown, the
     ADC's MCLK input, the bus window); 0231 and 0233 change `mendocino.c`
     (the codec's own link component, the BCLK polarity); 0235 changes the
     clocks (closest-rate MCLK dividers). Each patch's description gives the
     measurement behind it.
   - **The speaker's loudness follows Fire OS.** `pinna-board` gives this
     board Fire OS 8349's volume curve (`VolumeCurve::Steps`, read by TECHO5
     from `VolumeCurves.xml`), because LibreEcho's curve played 20 dB under
     Fire OS at half volume (C2N6L4, 2026-11-26). The mixer sets `Speaker
     Volume` to 10 (+14 dB, where Fire OS leaves the amplifier).
   - **The AFE routes and the ADC switches are written before PipeWire
     starts.** The PipeWire wrapper sets the routes and `CH1`-`CH3_ASI_EN`
     first, because UL9 won't open without a routed back end, and the ADC's
     switches are required: without them the microphones read exact zeros
     (C2N6L4, 2026-11-26).
   - **Not measured on this board:** the microphone level (the graph keeps
     the MT8163's +12.04 dB), and the tuning of the beam, the canceller and the
     wake word.

9. **Updates on the Echo Dot (5th gen)** (2026-11-26). Amends ADR 0019 and
   ADR 0022 for this board; the MT8163 and MT8516 Echos keep theirs.
   - **The board names its bootloader.** `Bootloader::Kaeru` (LK with the
     Kaeru payload: Android boot images, fastboot, a preloader that counts
     tries) or `Bootloader::AmazonUboot` (FIT boot images, a locked fastboot
     Pinna can't install through, and tries it counts itself). The
     boot image format, the fastboot guard, the recovery text and the
     updater's slot rules follow from it, not from the SoC or the storage. For a board Pinna doesn't
     describe, the two sides differ: `pinna-bootctl` takes the bootloader from
     the storage kind (UBI means Amazon's U-Boot), while `pinna-init`'s boot
     format and attempt counting fall back to Kaeru and Android images.
   - **The slot record is U-Boot's own.** Amazon's U-Boot reads the record
     Pinna writes, at `misc` 0x360 ("Boot Ctrl" magic, version 1, priority,
     tries and successful bits, no CRC): Pinna's `mark-good` set slot a's
     byte from 0xff to 0x8f and the next boot started slot a with the record
     unchanged (C2N6L4, 2026-11-26). It passes `androidboot.slot_suffix` and
     reads `boot_<slot>`, so the kernel's slot is the root's slot: an update
     writes the target slot's boot volume and root volume together.
   - **U-Boot counts the tries and falls back by itself** (C2N6L4,
     2026-11-26). This was first assumed otherwise, since the GPL U-Boot
     leaves the slot logic out. On the unit, every start lost one try before
     Linux ran (4 written, 3 left), and a trial slot with 2 tries was set to
     priority 0 by U-Boot after two starts, which then started the good
     slot. So `pinna-init` counts nothing on this board, as on Kaeru
     (`Bootloader::counts_tries()`); counting there too halved every trial.
     The tries mean what they mean on Kaeru: `attempts + 1`, a start takes
     one and needs one left. A kernel that never reaches `pinna-init` falls
     back too.
   - **U-Boot has a fastboot mode, locked** (`getvar secure: yes`,
     `version-bootloader: U-Boot 2019.04`, product `cannoli-lgoprb-v4-?`),
     which shows on USB as "USB download gadget" (1949:0660) with the ring
     blue. It stopped there twice: after a reset without a shutdown (no
     kernel message, most likely the hardware watchdog) and after the
     power was cut during a stuck shutdown; each time the trial slot it
     picked lost a try. `fastboot continue` resumed the start. A restart
     from Pinna into a trial slot didn't stop there: U-Boot started the new
     slot (C2N6L4, 2026-11-26). Its binary names a fastboot flag it sets and
     clears and the last reset's cause (`wdt_sta`, passed in `bootargs`);
     what sets the flag isn't known. The fastboot guard stays off on this
     board.
   - **The updater writes UBI volumes.** One resolver turns a slot name into
     the board's node: a GPT partition, or a UBI volume's character device.
     A UBI volume is replaced whole (`UBI_IOCVOLUP`, then the data in order)
     and read back. the updater, pinnad, `pinnactl` and `pinna-bootctl` share the resolver
     (`crates/pinna-bootctl/src/storage.rs`, commit 793ba94). `pinna-init`
     doesn't: it finds the slot's `ubiblock` device itself (`scan_ubi`).
   - **A release carries a boot image per boot format.** The manifest keeps
     `boot` (the Android boot image, which satellites before this read) and
     adds `boots`, a list of `{ "models", "url", "size", "sha256" }`; a
     satellite takes the entry naming its model. Only a board with Android
     boot images falls back to `boot`; a FIT board whose model has no entry is
     blocked (`NoBootImage`). The updater refuses a boot image of the wrong
     format, and a FIT whose device trees don't name both the SoC and the
     board family (`Bootloader::AmazonUboot { fit_board }`, `amzn,cannoli`;
     commit cc6f2ef). `requires.models` lists the models the release was built for.
   - **Each board states its slot sizes.** The root slot of the Echo Dot
     (5th gen) holds 131,088,384 bytes and U-Boot reads 0xC1C000 bytes of a
     boot volume (`bootimage_size`); the MT8163 Echos' are 768 MiB and
     16 MiB (ADR 0019). Sealing the root image and building the manifest
     fail when an image is larger than the smallest slot of the models it is
     for. One root serves every model, so the Echo Dot (5th gen)'s slot is
     the limit for all of them (the root image built on this branch, version
     0.6.0-dev.202611261631.gcdd0bf2, is 117,440,512 bytes: 13.0 MiB under).
   - **WPA3 stays off for the MT7663 until it is measured.** mt76 with
     wpa_supplicant should join SAE and PMF networks, but no join to a
     WPA3-only network has run on an Echo Dot (5th gen), so
     `Wifi::supports_sae` returns false for it as for the MT8163 (ADR 0008).
     pinnad's SAE join path is there for the day it is measured.
   - **Measured before the board is listed as updatable:** that U-Boot
     boots the slot with the higher priority, and an update from one slot to
     the other and back on a unit.

10. **Installing on the Echo Dot (5th gen)** (2026-11-26), roughly as on
    the Echo (2nd gen).
    - **The unlock is firebreak's.** It leaves rooted Fire OS in slot A and
      TWRP in slot B. USB is the test pads under the foot, as the Echo (2nd
      gen)'s is its base pins. Its bootloader's fastboot is locked
      (Decision 9), so the install can't use it.
    - **Pinna installs from TWRP, over adb.** `scripts/install-echo-dot-5.sh`,
      on the owner's computer, streams the release's FIT into `boot_a` and its
      root into `system_a` through a static `pinna-bootctl write-volume`
      (`adb shell -T`, nothing staged in TWRP's RAM), which replaces each UBI
      volume whole and checks it read back against its sha256. It then makes
      slot A the active slot on trial and reboots. `userdata` keeps its
      UBIFS, which Pinna mounts as `/var`.
    - **The way back:** while slot B is TWRP, a slot A that fails its
      starts falls back to it (U-Boot counts them, Decision 9), and holding
      Volume Up at power-on starts it. Pinna's rescue page works over
      the test pads' USB. firebreak's restore puts Fire OS back into slot A
      from the backup its unlock made with `--backup`, not `userdata` or
      slot B (firebreak's cannoli guide).
    - **The first update replaces TWRP.** An update writes the other slot, so
      after it both slots hold Pinna, as on the Echo (2nd gen). The install
      guide says so, and sends the owner to firebreak's guide before the
      first update.

## How the design keeps the goals

- **Be safe to install and update:** the Echo Dot (5th gen) keeps A/B slots
  (`boot_a`/`boot_b`, `system_a`/`system_b`) and a bootloader Pinna never
  writes, as on the MT8163 and MT8516. firebreak works over the
  test pads with no working system, so a satellite with both slots broken
  can still be recovered — the owner keeps the wires and a backup. Until it
  is shown on a unit that the bootloader boots Pinna's FIT by its slot record
  and that the updater can write a UBI volume safely, the port is not offered
  to owners.
- **Use standard parts:** the Wi-Fi, the Bluetooth, the codecs and the SoC
  peripherals are mainline drivers. The clocks, pinctrl, power domains and
  PMIC are rebased onto mainline's MediaTek cores and are candidates for
  upstream, as the MT8163 and MT8516 board support is. The audio front end is
  written the same way.
- **Stay open:** Amazon's speaker tuning is not committed. The MT7663's
  firmware is linux-firmware's, fetched from kernel.org and built into the
  kernel; the MT8163's and MT8516's firmware is fetched from
  `static.iodev.org`.
- **Make development pleasant:** one root image and one Rust toolchain for
  every satellite, 32-bit native on this SoC. The kernel build adds the
  `mt8519` variant; the virtual Echo Dot and its tests keep covering the
  userland all boards share.

## Consequences

- `pinna-bootimg` gains a `fit` module: a FIT builder (`fit-pack`) and a
  reader that prints a FIT's images and configurations (`fit-info`). Signing
  follows the bootloader's trust model, read on a unit.
- `pinna-init`, `pinna-bootctl` and the updater gain a UBI volume lookup
  beside the GPT one, chosen by the board's storage kind. The MT8519's slot
  record is read before they write it.
- `pinna-board` has an `EchoDot5` model and board (ADR 0032): the CPLD
  key codes, the `gpio-privacy` switch, the ring, the sound card with its
  ETDM PCMs and 3 microphones. It describes the parts on the owner's unit
  (Decision 8); another board revision needs its own measurements.
- `pinna-audio` has a 3-microphone front end with the reference on the AFE
  loopback, and a speaker path at the PCM's 96 kHz. The beamformer, the echo
  canceller and the wake word thresholds were tuned on the MT8163 array; they
  need measurements on this array before owners use it.
- The kernel grows from two board families to three. Each needs a device to
  test, and no CI runs device tests (AGENTS.md).
- The browser installer (ADR 0016) does not cover the Echo Dot (5th gen):
  its install needs soldered wires and a firmware-build check, so it stays a
  by-hand port until that changes.
- A unit has run Pinna's root from NAND and passed the A/B update and
  rollback test (2026-11-26), and captures its three microphones and the
  echo reference; how well it hears over music is not measured. Releases
  ship its installer and, for
  now, leave it out of the update manifest (`PINNA_MODELS`).
